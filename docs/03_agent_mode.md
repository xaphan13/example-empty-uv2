# Агентный режим — архитектура команды

## Для чего это

В проекте настроен **агентный режим** — команда специализированных AI-агентов, которыми управляет оркестратор (главная сессия Qwen Code). Оркестратор не пишет код, а п��анирует, делегирует, проверяет доказательства и принимает финальные решения.

## Команда

| Роль | Файл агента | Зона ответственности |
|---|---|---|
| **Оркестратор** | главная сессия | план, делегирование, ревью, триаж, финальное решение |
| **spec-writer** | `.qwen/agents/spec-writer.md` | фаза создания: превращает сырую идею в детальную спецификацию с планом фаз |
| **backend-dev** | `.qwen/agents/backend-dev.md` | Python-модули проекта, миграции |
| **frontend-dev** | `.qwen/agents/frontend-dev.md` | статические страницы (если есть) |
| **qa** | `.qwen/agents/qa.md` | проверка запуском, curl-прогоны, заметки e2e, ведение `DEFECTS.md` |
| **adversary** | `.qwen/agents/adversary.md` | враждебные прогоны, `ADVERSARIAL_REVIEW.md` |

Модели для каждой роли задаются в frontmatter `model:` соответствующего агент-файла. При переносе агентного режима в другой проект меняется только привязка к проекту, сами агенты универсальны.

## Жизненный цикл задания

### 1. Создание (фаза spec)

Пользователь кладёт сырую идею (2–10 строк) в `tasks/current/REQUIREMENTS.md` или сообщает её в чате. Оркестратор запускает скилл `task-spec`, который вызывает spec-writer. Тот:

- исследует зону задачи,
- пишет полный `REQUIREMENTS.md` с **планом фаз** (шаблон — `.qwen/skills/task-spec/TEMPLATE.md`),
- оркестратор ревьюит по чек-листу, закрывает открытые вопросы с пользователем,
- получает **подтверждение плана фаз** от пользователя.

После этого **спека замораживается** до конца задания — менять её может только оркестратор и только с явного согласия пользователя.

### 2. Исполнение (фазы разработки)

- Делегирование идёт строго по фазам из плана.
- **Одна фаза = одно делегирование = 1–3 файла = бюджет ~10–15 ходов.**
- Разработчик ведёт прогресс-файл `tasks/current/dev/phaseNN_progress.md`.
- После завершения фазы — оркестратор делает **ревью диффа и чекпоинт**:
  - дифф соответствует фазе,
  - `ruff` чист,
  - счётчики (маршруты, функции и т.п.) сходятся,
  - лишнего не написано.
- Следующая фаза стартует только после **зелёного чекпоинта**.

Если прогон разработчика упал — восстановление идёт **свежим узким запуском** по прогресс-файлу и `git diff`, а не пересказом всей истории сессии.

### 3. Проверка (qa)

Когда все фазы закрыты, оркестратор поручает qa:

- запустить приложение,
- прогнать curl-сценарии из критериев успеха,
- проверить регресс соседних эндпоинтов,
- записать сырые выводы в `tasks/current/e2e/`.

В спецификацию qa передаётся готовый блок проверок. Если сервер уже поднят — qa использует его и не поднимает второй.

### 4. Враждебный прогон (adversary)

Оркестратор отправляет adversary на короткий враждебный прогон по изменённой функциональности. Каждая находка из `ADVERSARIAL_REVIEW.md` получает триаж:

- **ACCEPTED** → поручить qa воспроизвести и завести `DEF-NNN`.
- **REJECTED** → записать причину.

Ни одна запись не остаётся PENDING при закрытии задания.

### 5. Проверка критериев успеха

Оркестратор проходит все критерии из `REQUIREMENTS.md` один за другим. Каждый должен подтверждаться **доказательством** — curl-выводом, логом или заметкой из `e2e/`. Только после этого задание считается выполненным.

### 6. Архивирование

Оркестратор:

1. Переименовывает `tasks/current/` → `tasks/NNN-<slug>/` (номер — следующий порядковый, slug — латинское имя через дефис).
2. Убирает из `REQUIREMENTS.md` пометку «Текущее задание».
3. Дописывает в конец **Отчёт о выполнении** (шаблон — в `QWEN.md`):
   - дата закрытия,
   - итог,
   - таблица критериев с результатами и ссылками на доказательства,
   - список дефектов,
   - disposition находок adversary,
   - участники.
4. Создаёт свежую `tasks/current/REQUIREMENTS.md` с заглушкой «Задания нет» (или сразу с новым заданием, если пользователь его выдал).

### 7. Остановка серверов

После закрытия задания оркестратор гасит все тестовые процессы (`pgrep -af "uvicorn.*main:main_app"` → kill). Сервер нужен только на время живого задания.

## Дефекты (DEFECTS.md)

- Новые дефекты заводит **qa** в `tasks/current/DEFECTS.md`.
- Оркестратор отправляет OPEN-дефекты (начиная с наивысшей серьёзности) нужному разработчику.
- Разработчик отвечает одним из: **ИСПРАВЛЕНО**, **НЕ ВОСПРОИЗВОДИТСЯ**, **РАБОТАЕТ КАК ЗАДУМАНО**.
- Оркестратор записывает ответ в `DEFECTS.md` как **FIX-READY** или **DISPUTED**.
- Дефект закрывает только **qa**, после перепроверки.
- Оркестратор может установить **REJECTED** с письменной причиной, если исправления не будет.

## Дисциплина затрат

Трать модель на суждения, а не на набор текста:

- Оркестратор **не пишет и не редактирует код** (только markdown-файлы: планы, DEFECTS.md, disposition, документацию).
- Читай диффы и сводки, а не целые деревья исходников.
- Не микроуправляй в середине задачи — дай субагентам закончить.
- Запуск приложения и проверки — задача субагентов.

**Главный источник перерасхода — backend-dev.** Три уровня защиты:

1. **Спека с планом фаз** — объём режется заранее в дешёвой сессии исследования.
2. **Короткие фазы** — 1–3 файла, бюджет ~10–15 ходов.
3. **Дисциплина внутри фазы** — план до первой записи, новый файл — одним `write_file`, существующий — точечным `edit`, сырые выводы — сразу в `dev/`, чекпоинт после каждого файла.

**Дорогое восстановление — главный скрытый расход.** Упавший прогон восстанавливай свежим узким запуском «фаза N: сделано X, доделай Y» по прогресс-файлу и `git diff`, а не пересказом истории сессии. Перед перезапуском проверь, что упавший прогон не оставил процессов и мусорных файлов.

## Что нельзя трогать агентам

Общее для всех субагентов: **не редактировать**:

- `.qwen/` (конфигурация агентов),
- `tasks/current/REQUIREMENTS.md` (после старта исполнения),
- папки архивных заданий `tasks/NNN-*`,
- `AGENTS.md`, `QWEN.md`, `README.md`,
- `docs/` (кроме случаев, когда оркестратор явно координирует обновление).

**Единственное исключение:** spec-writer на фазе создания пишет `tasks/current/REQUIREMENTS.md` одним `write_file` по шаблону.

Не добавлять зависимости и тестовые фреймворки без решения оркестратора.
